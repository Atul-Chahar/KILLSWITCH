# Safety Model & Guardrail Specifications

KILLSWITCH is engineered around an uncompromising safety axiom:
**The model proposes. Plain code verifies. A human approves.**

No automated system or large language model is ever granted autonomous destructive access to cloud infrastructure. Every destructive invocation must survive four layered defenses before executing.

---

## 1. The Four Layer Defense Boundary

```
[Layer 1: Read Isolation]
CloudTrail LookupEvents + IAM Inspection (Read-Only IAM Permissions)
                 │
                 ▼
[Layer 2: Deterministic Provenance Verification]
Pure Python AST-Checked Verifier (Zero Network, Zero Model, Zero AWS SDK)
                 │
                 ▼
[Layer 3: Human Authorization & Task Token Gate]
Cedar Policy Evaluation + Step Functions waitForTaskToken (Operator Console)
                 │
                 ▼
[Layer 4: Token-Scoped Execution & Confirmation]
Round-Bound Approval Tokens + Post-Action API State Verification
```

---

## 2. Layer 1: Read Isolation

The investigation phase is strictly read-only.
- **IAM Boundaries**: The `investigate` Lambda role possesses only `cloudtrail:LookupEvents`, `iam:ListAccessKeys`, `iam:GetAccessKeyLastUsed`, and `iam:GetUser`. It cannot create, modify, or terminate any resource.
- **Untrusted Agent Sandbox**: The Strands agent running on Amazon Bedrock (`narrate/agent.py`) is instantiated with `tools=[]`. It possesses zero write tools, zero read tools, and zero execution callbacks. It cannot inspect the filesystem, initiate network requests, or trigger AWS APIs. It acts purely as a structured transformer turning evidence JSON into a proposed action plan.
- **One-Turn Enforcement**: The agent is locked to `limits={"turns": 1}`. When an agent model returns a schema failure, Strands by default returns the error to the model to retry. KILLSWITCH disables this behavior to prevent an untrusted model from negotiating or attempting adversarial prompt injection against schema validation.

---

## 3. Layer 2: Deterministic Provenance Verifier

The verifier (`verifier/verify.py`) evaluates proposed actions against the recorded CloudTrail `BlastRadius`.

### Invariants Enforced
1. **Ownership**: An action targeting an EC2 instance is rejected unless the exact `instance_id` appears in CloudTrail as a `RunInstances` event initiated by the compromised `access_key_id` in the specified region.
2. **Region Alignment**: Instances are region-scoped. An action proposing a real instance ID in the wrong region is rejected immediately.
3. **Allow-List Actions**: The verifier only recognizes an explicit allow-list of action types (`deactivate_key`, `terminate_instance`, `open_pull_request`). Any unlisted action type fails closed (`UNKNOWN_ACTION_TYPE`).
4. **Key Pinning**: Key deactivations must match the incident's leaked key or a secondary key minted by the attacker (`CreateAccessKey`). Foreign keys are rejected.
5. **No Code Impurity**: The verifier consists of pure mathematical functions. `tests/test_verifier.py:test_verifier_imports_are_pure` parses `verifier/verify.py` via Python's Abstract Syntax Tree (AST) on every build, failing the build if `boto3`, `botocore`, `strands`, `requests`, `urllib`, or `http` are imported.

---

## 4. Layer 3: Cedar Policy & The Human Gate

Authorization separates actions into risk tiers:
- **Low Risk / Non-Destructive**: Read operations and resource tagging can proceed autonomously if configured.
- **High Risk / Destructive**: Any action that terminates compute (`terminate_instance`) or disables credentials (`deactivate_key`) is classified by Cedar policies (`authorize/policies/containment.cedar`) as requiring explicit operator approval.
- **Step Functions Pause**: The approval step is executed via `lambda:invoke.waitForTaskToken`. The execution token is generated by AWS Step Functions and held securely in DynamoDB. The state machine cannot proceed until an authenticated human operator approves the action via the console.
- **No Autopilot Fallback**: If the Verified Permissions policy store is unreachable, the system falls back to a hardcoded fail-safe table where all destructive actions require human confirmation.

---

## 5. Layer 4: Cryptographic Approval Tokens & Scoped Containment

When an operator clicks "Approve", the API issues an approval token with strict cryptographic and contextual scoping:
- **Signature Composition**: Tokens are bound to the `incident_id`, the specific `action_id`, the target resource ARN, and the incremental `approval_round` ID.
- **Guard Validation**: Functions in `containment/actions.py` (`deactivate_key`, `terminate_instance`) call `containment/guard.py:require_approval_token`. If the token is missing, invalid, or belongs to a superseded round, execution raises `UnauthorizedActionError` and logs a security violation.
- **Single Blast-Shield IAM Statement**: In CDK synthesis, only a single IAM policy statement attached to the containment Lambda grants `ec2:TerminateInstances` and `iam:UpdateAccessKey`. `tests/test_response_stack.py` validates the synthesized CloudFormation template to verify that no other role in the account possesses these permissions.
- **Session Revocation**: In addition to deactivating credentials, containment attaches an inline IAM deny-all policy conditioned on `aws:TokenIssueTime`, invalidating existing STS temporary credentials and active sessions.

---

## 6. Post-Action Confirmation

KILLSWITCH never rounds up an API acknowledgment to success:
- After invoking `ec2:TerminateInstances`, `containment/end_state.py` polls EC2 to verify the instance is in the `shutting-down` or `terminated` state.
- After calling `iam:UpdateAccessKey`, it re-reads IAM to verify `Status == "Inactive"`.
- If an action was denied by the human operator, the target resource is untouched, logged as `declined`, and the incident ends cleanly in a `declined` state rather than failing.
- If an approved action fails to reach its verified target state, the entire Step Functions execution transitions to `Fail`.
